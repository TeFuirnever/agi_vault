# OpenClaw 二开 Windows 客户端可行性报告

- 文档版本：v1.0
- 生成日期：2026-02-07
- 作者：By Codex
- 目标目录：`E:\agi_vault\JavaProject`

## 1. 结论

基于 OpenClaw 二次开发 Windows 客户端**可行性高**。

核心原因：

1. OpenClaw 已具备稳定的 Gateway 控制平面（WebSocket/HTTP）。
2. 现有 Web 控制台与协议能力可复用，客户端可采用“薄客户端 + Gateway”模式快速落地。
3. Windows 运行与服务化路径已有工程基础（Scheduled Task 相关实现）。

## 2. 可行性评估

### 2.1 技术可行性：高

- 客户端主要实现连接、鉴权、会话交互、状态展示，不必重写 AI 核心执行逻辑。
- Gateway 已承担渠道接入、Agent 调度、节点能力与会话状态。

### 2.2 工程可行性：高

- 可复用现有 `ui/` 逻辑与交互模式。
- 可基于现有协议（`connect` / `hello-ok` / req-res / event）直接对接。

### 2.3 交付可行性：中高

- MVP 预计 4-8 周可达成（视技术路线与团队经验而定）。

### 2.4 风险可控性：中

- 主要风险集中在：连接安全链路、Windows 本地权限/安装分发、UI 状态复杂度。

## 3. 推荐架构

推荐采用：**Windows 客户端（UI 与本地体验） + 外置 OpenClaw Gateway（控制平面）**。

职责划分：

1. 客户端：UI、连接管理、凭据管理、系统集成（托盘/通知等）。
2. Gateway：会话、Agent 执行、渠道路由、节点调用、配置与事件广播。

数据流：

1. 客户端通过 WS 连接 Gateway。
2. 客户端发起 req（chat/config/status 等）。
3. Gateway 推送 event（agent/chat/presence/tick 等）。

## 4. 技术路线对比

### 4.1 Tauri + 现有 Web UI（优先推荐）

优点：

1. 复用率高，首版上线快。
2. 包体与内存占用通常优于 Electron。

风险：

1. 需要 Rust/Tauri 构建链能力。

### 4.2 Electron + 现有 Web UI

优点：

1. 生态成熟，开发门槛低。

风险：

1. 资源占用较高，包体较大。

### 4.3 WinUI/WPF 原生

优点：

1. 原生体验最佳，系统集成能力强。

风险：

1. 首版周期较长，现有 Web 复用率低。

## 5. 关键风险与缓解

### 风险 1：鉴权与配对链路复杂

缓解：

1. 严格复用现有 Gateway 协议语义，不在首版改服务端鉴权模型。
2. 先实现 token/password + device identity 的最小闭环。

### 风险 2：Windows 权限与分发复杂

缓解：

1. 首版采用用户态安装与运行。
2. 二期再引入企业分发策略（签名/MSI/自动更新）。

### 风险 3：首版范围膨胀

缓解：

1. 锁定 MVP，只做“连接 + 聊天 + 状态/日志 + 基础配置”。

### 风险 4：UI 状态复杂度过高

缓解：

1. 按连接层、会话层、审批层、配置层拆分模块。

## 6. MVP 范围建议

1. 连接与会话：Gateway URL、鉴权、连接状态、自动重连。
2. 聊天流程：会话列表、消息发送、流式回复展示、中断。
3. 运维基础：health/status/logs 查看。
4. 配置基础：读取/更新关键配置项。

## 7. 投入预估（参考）

1. 1-2 名工程师，MVP：4-8 周。
2. 全量对齐 Web 控制台：8-16 周。
3. 全原生深度系统集成：12 周以上。

## 8. 最终建议

1. 首版采用“外置 Gateway + 复用现有 Web 能力”。
2. 技术路线优先级（按性价比）：Tauri > Electron > 全原生。
3. 先打通业务闭环，再逐步增强原生能力（托盘、通知、自启动、更新）。
